# BS11 の録画が 13 時間止まっていた件と、監視の穴（2026-11-23）

DT295 個体（`192.168.99.123`）の BS11 が 04:05 から 17:32 まで録画できていなかった。
原因は 2 つで、どちらも「気づけない」方向に働いていた。両方を直した。

## 1. 何が起きていたか

| 時刻 | 出来事 |
| --- | --- |
| 04:05 | BS11 の最後の録画ファイル。以後ファイルが増えない |
| 04:05〜17:30 | 装置は `capturing: true` を返し続け、`totalPushed` は 34531 で凍結 |
| 毎時 | ガードが `S97 start` を実行し「stream restarted over ssh」と記録（実際は無変更） |
| 毎 10 分 | 監査が `node_progressing` を記録（実際は 1,212 バイトの空スタブ） |
| 17:25 | ダッシュボード（`:40776`）で `stalled` に気づく |
| 17:32 | 復旧。`totalPushed` が進み始める |

## 2. 直接の原因

停止マーカーと所有権マーカーが、死んだ PID を指したまま残っていた。

```
/var/run/pix-stream.stopped     8312（死亡）
/var/run/pix-stream.owner/pid    314（死亡）
```

`S97pix-stream start` は次の 2 か所で止まる。

- `[ ! -e "$STOPFILE" ] || echo 'stop requested'; return 1`（停止要求が残っている）
- `[ ! -d "$OWNER" ] || echo 'previous owner not drained'; return 1`（所有権が残っている）

停止・再起動の処理が途中で落ちると、この 2 つが残る。以後どんな `start` も起動しない。
`restart` も `stop` が `children did not drain` で失敗するため通らない。

つまり「停止要求を書いた主体が死んだ後、誰もその要求を取り消せない」状態だった。

## 3. 気づけなかった原因

### 3.1 ガードが復旧したと誤認していた

`nas/src/pix-stb-guard.py` の `restart_stream()` は、`S97 start` の終了コードと
`/v1/status` の HTTP 200 だけで成功を判断していた。

- `start` は「すでに動いている」場合も 0 を返す
- `/v1/status` は `stb_streamer` 単体が返すため、映像経路が死んでいても 200 を返す

結果、13 時間毎時「復旧成功」と記録し続けた。実際のログの最後の 1 行も
`192.168.99.123: stream restarted over ssh` である。

### 3.2 監査が停滞を「進行中」と判定していた

`nas/src/pix-recording-audit.py` の停滞判定は、ステージングファイルの
「サイズ > 0」と「mtime が 90 秒以内」だけを見ていた。

レコーダーは媒体が取れなくても 1,212 バイトのスタブを書き直し続ける。そのため
`bytes: 1212`、`age_sec: 7.7` が「進行中」の条件を満たし、`node_progressing`
（info）が記録され続けた。`node_stalled` は 11-21 を最後に出ていない。

## 4. 直したこと

### 4.1 装置の復旧（即時）

1. 死んだ PID を指す停止マーカーと所有権マーカーを削除
2. `S97pix-stream start`
3. `/v1/status` の `totalPushed` が 7 → 21 → 92 と進むことを確認
4. レコーダーが自動で再生成され、ステージングが約 1 MB/s で伸びることを確認

### 4.2 ガード（`nas/src/pix-stb-guard.py`）

| 変更 | 内容 |
| --- | --- |
| 復旧の実体 | `S97 restart` を使う |
| 成功判定 | `totalPushed` が 40 秒以内に 3 以上進んだときだけ成功 |
| 途中終了の修復 | 進行しなければ、死んだ PID を指すマーカーだけを消して `start` し直す |
| 生きている所有者 | `held` と判断して触らない（安全側） |
| 失敗時 | 「物理確認が要る」と記録する（成功と書かない） |

`--self-test` に、カウンタの前進判定（0 に戻る再起動を含む）を追加した。

### 4.3 監査（`nas/src/pix-recording-audit.py`）

進行中の条件に下限を入れた。実キャプチャは 1 MB/s で書くので、1 MB 未満は
「データが来ていない」と扱う。

```python
STAGING_MIN_BYTES = 1 << 20
progressing = staging.bytes >= STAGING_MIN_BYTES and staging.age_sec <= 90
```

この条件では、今回の 1,212 バイトのスタブは `node_stalled`（warn）になる。

### 4.4 配備

| 対象 | 置き場所 | 控え |
| --- | --- | --- |
| ガード | `/home/ku/pix-stream-20261101/pix-stb-guard.py` | `.before-20261123` |
| 監査 | `/home/ku/pix-recording-audit/pix-recording-audit.py` | `.before-20261123` |

ガードは再起動済み。監査は 1 回実行して、3 ノードすべてが `recording`、
ステージングが GB 単位であることを確認した。

## 5. 残っていた弱点と、その対処（同日 18:00 追記）

| 弱点 | 対処 |
| --- | --- |
| 装置単体では復旧できない | `pix-stream-unfence` を追加し、S97 の start が自分で死んだマーカーを片付ける |
| 停止マーカーの主体が分からない | 解除時に `/var/run/pix-stream.fence.log` へ PID と時刻を残す |
| 週次ロゴ取得が 6 時間ごとに失敗する | `dt295` 以外の機体では週次を止める（ログは 1 回だけ） |
| ストリーマが `capturing: true` を返す | ガードと監査は `totalPushed` の前進で判断する（変更済み） |

### 5.1 解除の持ち主を 1 か所にした

`/usr/bin/pix-stream-unfence` が、停止マーカーと所有権を消してよいかを決める。

| 状態 | 出力 |
| --- | --- |
| マーカーが無い | `none` |
| 所有者の PID が生きている | `held`（消さない） |
| 所有者も worker も死んでいる | `cleared`（消す） |

owner の pid だけでなく `worker.<pid>` の生存も見る。親だけ死んで子が残っている
状態で消すと、二重に起動してしまうため。

S97 の `start` は最初にこれを呼び、`held` なら従来どおり拒否する。これで
NAS のガードが落ちていても、装置は次の起動要求で自分を直せる。

### 5.2 ガードは「流れたこと」だけを見る

マーカーの解除は S97 の持ち物になったので、ガードからは解除処理を外した。
ガードは再起動を要求し、`totalPushed` が 40 秒で 3 以上進んだときだけ成功とする。
進まなければ `start` をもう一度試し、それでも駄目なら物理確認が要ると記録する。

### 5.3 実機での確認

| 項目 | 結果 |
| --- | --- |
| `pix-stream-unfence` | 稼働中は `held` を返す（`owner` の PID が生存） |
| 装置のキャプチャ | 2 本の ffmpeg が継続、録画は止まっていない |
| ガード | `--self-test` 通過、再起動後 active |
| 監査 | 3 ノードとも `recording`、ステージングは GB 単位 |

## 6. 調査の再精査（次に進めるもの）

[cm-amatsukaze-research-20261123](cm-amatsukaze-research-20261123.md) の候補を、
今日の実測を踏まえて並べ直した。

| 優先 | 項目 | 判断 |
| --- | --- | --- |
| 1 | 人手ラベルの拡充と scenario 公開の判断 | 最大の拡大余地（6 日で 94 本＝17%）。公開の可否はラベルでしか決められない |
| 2 | 局別プロファイル | A/B の型ができたので、特徴量を残したまま局別に測れる。コスト小 |
| 3 | PMT 更新の sideband 化 | 頭尾の確定に効くが STB 側の改修が要る。まず 3 局が PMT を更新するかの測定から |
| 4 | CutMrg の自動検出 | **優先度を下げた**。終端は既に 0.03 秒で、始端のずれは内容（番宣）由来であり、系統的なオフセットではない |
| 5 | ロゴ学習の強化（C++） | 直近の共通化で主要因は解消済み。次の失敗率を見てから |

今回の障害から得た新しい判断:

- **録画の完全性が精度の前提**である。13 時間の欠落は、CM 判定の精度より先に効く
- 監視の主体を増やさない。ガードと監査の 2 つで、停止と停滞の両方を持つ。
  3 つ目を足すと同じ判定を 2 か所で保守することになる
- ガードの成功条件は「データが流れたこと」に限る。HTTP の応答は成功の証拠にならない
