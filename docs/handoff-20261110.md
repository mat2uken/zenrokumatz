## 起動で判明したこと

既存U-Bootは2015.01。`booti` とFAT読み込みに対応するが、`bdinfo`、`ext4load`、独立した `part` はない。autoboot待ちは約1秒なので、再起動ログの停止表示を検出したらすぐ空白を送る。動いているLinuxの確認に再起動は不要である。

Imageは `0x01080000`、DTBは `0x08000000` にロードする。`fdt_addr_r`、`dtb_mem_addr`、`fdtaddr` をDTBと同じ値にする。以前のDTB読込み先 `0x01000000` は、`booti` 後にマジックが壊れて起動に失敗した。Image再配置による上書きが疑われ、DTB移動後は起動した。上書き処理そのものの解析は未完了だが、成功済み手順で旧アドレスへ戻す必要はない。

vendor U-Bootの予約メモリー処理で `FDT_ERR_NOTFOUND`／`rsvmem fdt get prop fail` が出ても、その後Linuxへ制御が渡った。この警告だけを理由にAndroid用DTBを適用したり、予約領域を削除したりしない。`saveenv`、eMMC書込み、U-Boot交換、SD優先起動の永続化は未実施で、今回の引継ぎでも自動的に追加しない。

## 残作業のレビューと進める順序

### 0. TS→H.264/AAC→MP4（2026-11-10の後半から最優先）

ユーザーの指示で、チューナー受信より先に「TSからハードウェアデコードとハードウェアエンコードでH.264/AACのMP4を作る」工程へ順番を変えた。TSはUSBチューナーを待たず、mirakc（`192.168.99.40:40772`）または合成TSで用意する方針。

**済んでいること。** ffmpeg 6.1.5を `configs/x96max_defconfig` に追加してrootfsへ組み込み、`mpeg2_v4l2m2m`（デコード）・`h264_v4l2m2m`（エンコード）・mp4 muxerが使えることを実機で確認した。VDECは `board/x96max/patches/linux/0001-vdec-meson-sm1-codecs.patch` で `meson-sm1-codecs` の `vdec/` に差し替え、G12Aのプラットフォーム表とMPEG-2のcanvas修正が入るようにした（`BR2_GLOBAL_PATCH_DIR` を追加済み）。ファームウェア `meson/vdec/gxl_mpeg12.bin` と `meson/venc/ga_h264_enc_cabac.bin` はoverlayの `lib/firmware` に置き、取得元とハッシュを `sources.lock.json` に記録した。

**原因を2つ特定して修正した。** 1つ目は起動順で、ffmpegはOUTPUTキューを先にSTREAMONするため、`codec_mpeg12_start()` の `amvdec_set_canvases()` がキャプチャキュー0件のまま走り、ファームウェアのバッファ番号との対応表が空になっていた（計測で `mapped 0 dst bufs`、ISR時点では `ready=7`）。`vdec.c` の開始条件を「出力とキャプチャの両キューがstreaming」に変えたところ `mapped 8 dst bufs` になり、`Buffer N done but it doesn't exist in m2m_ctx` は消えた。2つ目はEOSで、MPEG-12コーデックに `drain` が無く、CMD_STOP後にLASTバッファが返らないためffmpegが完了を待ち続けていた。`amvdec_dst_buf_done_empty_last()` を呼ぶ `codec_mpeg12_drain()` を追加して解消した。

**さらに2つ直した。** 画素読み出しのsegfaultは、プレーンサイズが `ALIGN(w*h, 64K)` = 1,572,864 なのに実ストライドが64境界で 1472×1080 = 1,589,760 になり、バッファ末尾を越えていたことだった。`bytesperline` は64境界のままにし、MPEG-12へ `canvas_height_align = 32` を入れてプレーンを `ALIGN(w,64)×ALIGN(h,32)` = 1,601,536 バイトへ広げて解消した。`-f rawvideo` で1フレーム 2,332,800 バイトが正しく出ることを確認した。EOSは、`drain` がteardownでもLASTを出していたため、`cmd_stop` フラグをセッションに足し、`V4L2_DEC_CMD_STOP` を受けたときだけLASTを出すようにした。

**デコードは実時間入力で完成した。** 入力レートを実時間にすると（`ffmpeg -re`）最後まで通り、10秒のMPEG-2 TSから299フレーム（PTS 0〜298、各2,332,800バイト）を出力した。ソフトウェアデコードとのPSNRは平均66.8 dB（Y 68.3、U 64.8、V 64.7）で、IDCT丸めだけの差に収まっている。ライブTSは実時間で届くため、想定するパイプラインはこの経路で成立する。

**残っている制約。** ファイルを一気に読み込ませると（`-re` なし）、入力長によらず1.4〜8秒で止まる。深いFIFOを渡すとファームウェアが途中で完了を返さなくなるためで、FIFOに余裕を残すバックプレッシャー（4 MiB／12 MiB／13 MiB）、パケット単位の入力pacing（`can_queue_input` で未処理2〜8パケットに制限）、drainのFIFO待ち（5秒／30秒）を試したが、いずれも途中で止まった（最も良くて13 MiB予約で7.9秒、8パケット窓で5.0秒）。根本原因はパーサFIFOが深いときのファームウェアの挙動で、次に追うなら `input_queued_buf` でOUTPUTバッファを絵が返るまで保持し、1パケット＝1フレームで流す構造に変える。実運用のライブTSは実時間で届くため、`-re` 相当の入力で問題なく通る。

ドライバの修正は `board/x96max/patches/linux/0001-vdec-meson-sm1-codecs.patch` に6点（両キュー起動待ち・bytesperline 64境界・canvas_height_align 32・cmd_stopフラグ・drainのFIFO待ち・async_drain）をまとめて再生成済み。実機に入っているモジュールは計測用printk付きなので、次のビルドで差し替える。

**ハードウェアH.264エンコーダーもG12Aで動作した。** `venc-h264/` はSM1前提で、`compat.h` の `get_cpu_type()` がSM1固定、`compat.c` が `amlogic,sm1-vdec` を探す。この2点をG12Aへ変え、6.18.62で `v4l2_m2m_buf_copy_metadata()` が3引数になった差分を直すだけでビルドが通った。実機では `amvenc: dos [mem 0xff620000-0xff62ffff] irq 23 canvas 0..11` と表示され、`/dev/video1` が作られる。SM1で使うSPI 45の決め打ちがG12Aでもそのまま当たった。

検証は3段階。720p30の合成入力を2 MbpsでエンコードしてPSNR 45.5 dB、1440x1080のパイプラインでPSNR 43.1 dB（Y 44.1、10秒299フレーム、要求6 Mbpsに対して実測6.6 Mbps、実時間の1.05倍）。ffmpegの1コマンドで通る。

```sh
ffmpeg -re -c:v mpeg2_v4l2m2m -i input.ts -an -vf "copy,format=nv12" \
       -c:v h264_v4l2m2m -b:v 6000k -g 60 out.mp4
```

**`-vf copy` が要る理由。** ffmpegのv4l2m2mエンコーダーは、入力フレームを元のlinesizeのままV4L2バッファへmemcpyする（`v4l2_buffer_swframe_to_buf()` が `frame->linesize` でサイズを決める）。一方エンコーダーは32境界の固定ストライド（1440なら1440）で読むため、デコーダーの64境界フレーム（1472）をそのまま渡すと1行あたり32バイトずれて斜め縞になる。`copy` フィルタで32境界に詰め直すと一致する。エンコーダー側を64境界へ変える試みは効かなかった（PSNR 8.8 dBのまま）。二重コピーの分だけ余計だが、1080p30で実時間の1.05倍を保てている。

**Buildrootへ組み込んだ。** `package/meson-venc/` を追加し、`BR2_PACKAGE_MESON_VENC=y` で `kernel-module` インフラからビルドする。`output/rootfs.ext4` には `/lib/modules/6.18.62/updates/amvenc_avc.ko` が入り、`modules.dep` にも載り、overlayの `amenc.conf`（`amvenc_avc`）と `meson/venc/ga_h264_enc_cabac.bin` と合わせて起動時に読み込まれる。SDを作り直せば手動insmodは不要になる。

**音声AACと1080iも通した。** AACはソフトウェアで180〜198 kbps、`-c:a aac` だけで通る。1080iは `bwdif=mode=send_frame` を挟むと実時間の1.04倍で29.97pになり、フレーム落ちも縞もない。コピーを挟まないぶん `copy` は不要になる。

**実放送TSで通した。** チューナー機（192.168.99.209、adb接続）の `/data/local/tmp/dtv_input.ts` は1440x1080i・MPEG-2・AACの実放送で、これを実機で処理した。ハードウェアデコードは110フレームでソフトウェアデコードと一致し、H.264 110フレーム＋AAC 198フレームのMP4（4.2秒、3.8 MB）になった。

```sh
ffmpeg -re -c:v mpeg2_v4l2m2m -i input.ts -vf "setpts=N/FR/TB,copy,format=nv12" \
       -c:v h264_v4l2m2m -b:v 6000k -c:a aac -b:a 192k out.mp4
```

`setpts=N/FR/TB` は、キャプチャしたファイルの最終フレームに飛んだPTS（90000分の128719）が付き、muxerが隙間を埋めるためにフレームを水増しして数百MBに膨れるのを防ぐため。ライブ入力では起こらない可能性が高いが、無害なので入れておく。

残る制約はデコードのバースト入力（`-re` 必須）と、SDの再作成がまだであること。

### 1. 現状確認と有線LAN

**有線LANは同日の追加セッションで完了した。** UARTから `uname -a`、root mount、`ip addr show`、`ip link show`、`lsusb` を確認するところから始める。BusyBoxの `ip` は `-br` に非対応。すでに取得した起動ログ全体の採取を繰り返す必要はない。

ケーブルを差し直すとLEDが点灯し、`carrier=1`、`operstate=up`、100 Mbps/Full、`Link is Up - 100Mbps/Full - flow control rx/tx` になった。DHCPは背景のudhcpcがそのままリースを取り、`192.168.99.109/24`、default via `192.168.99.254`、DNS `192.168.99.250`（`example.com` を解決）を得た。ゲートウェイ `192.168.99.1` へ3/3、ホスト `192.168.99.24`（macOS）へ3/3、ホストから本体へも3/3で疎通した。完了条件のリンク・IP・疎通は満たしている。

### 2. CPU電圧PWMとメモリーの切り分け

**PWMは同日の追加セッションで実機確認まで完了した。** 初期状態は `lsmod` がipv6のみ、`/sys/class/pwm` が空、cpufreqディレクトリが無く、`pwm-meson.ko` はrootfsに存在した。DTには `pwm@19000`（APB）と `pwm@2000`（AO）が `okay` で存在し、`regulator-vddcpu` はphandle 75のPWMを要求していた。`modprobe pwm_meson` を1回実行すると `pwmchip0/1` が登録され、`pwm-regulator` と `cpufreq-dt` の遅延プローブが解消した。CPU0-3が `schedutil` で1.0〜1.8 GHzのOPPを持ち、`VDDCPU` は730,030 µV・enabled、`cpu-thermal` は41.8 °Cを返した。モジュール読込み以外は変更していない。

原因はBuildrootがudevデーモンを持たない構成で、platform modaliasによる自動読込みが起きないことである。最小の修正として `board/x96max/linux.fragment` に `CONFIG_PWM_MESON=y` を追加し、`linux-reconfigure` と通常ビルドでビルド番号#2の `output/Image`（SHA-256 `96ab868f53df4fd772301cd8741915c1b50ef0eeed6ea30848a40e569bea1945`）を作成した。SDのFAT区画 `X96BOOT` の `Image` だけをこの成果物へ差し替え（DTBのハッシュで媒体を確認し、コピー後にSHA-256を照合）、U-Bootのautobootを止めて手動起動した結果、**モジュールを読まずに** `pwmchip0/1`・`cpufreq-dt`（1.0〜1.8 GHz、`scaling_cur_freq` が負荷に応じて1.2→1.6 GHzへ変化）・`VDDCPU` 730,030 µV が揃い、`cpufreq-dt`／`regulator-vddcpu` の遅延プローブ警告は消えた。**修正は実機で検証済み。** rootfsは#1のままなので `/lib/modules/6.18.62` に不要な `pwm-meson.ko` が残るが動作に影響しない。電圧やクロックを推測で固定しない。

メモリーについては、作成したDTSが2 GiBなのに対し、Linuxの稼働中DT `/sys/firmware/devicetree/base/memory@0/reg` の末尾は `78 00 00 00`、すなわち `0x78000000` だった。初期ログも1,966,080 KiBで一致する。`MemTotal=1,851,464 kB` はさらに予約領域などを差し引いた値で、2 GiBとの差をすべてCMAと解釈してはいけない。CMAは別に256 MiBの予約が記録されている。

起動過程でメモリー記述が変わったことを出発点に、必要ならU-BootのDT修正処理と実際の予約領域を調べる。128 MiBを使えるようにする変更は、この範囲を予約している理由を確かめてから判断する。起動可能なメモリー構成はすでにあるため、容量の回復をチューナー受信の必須条件にはしない。

PWM側の完了条件は満たした（残るのは新しいImageでの再起動確認だけ）。メモリー側は、縮小の事実・原因の確度・残る制約を記録することが完了条件。CPU周波数は1.0〜1.8 GHz、温度は `cpu-thermal` で読めるようになったため、速度評価の前提は整った。

Wi-Fi用 `wifi32k`／`sdio-pwrseq`、HDMI/VPUの初期化・同期待ちは記録済み。Wi-Fiと表示出力は初期用途に不要なので、警告を消すためだけの修正を追加しない。コーデックが必要とするVPU側の電源・clock・canvasとの関係は、エンコーダー移植時に確認する。

### 4. G12AのSoC H.264エンコーダー単体

候補は `sources.lock.json` に固定した `meson-sm1-codecs` の `eb7a44464af1c7793f793698e309abe4e6ad82da`。ソースの取得・移植・組込み・実機試験はまだ行っていない。対象がSM1で、G12A用DTBだけでは動かないことをコードで確認している。

### NAS への配信構成

NAS は既存の dtv_android と同じ経路で STB から pull する。STB 側は
`siano-ts -> torne-b25 -> ffmpeg -> ffmpeg -> stb_streamer` の 5 段で、
`stb_streamer` が `ram_spool` に断片を積み `stb_http` で配る。

**ffmpeg を 2 段に分ける理由。** `h264_v4l2m2m` は extradata を出さない。
1 本の ffmpeg で fMP4 をパイプへ書くと、`+empty_moov` が moov を先に書くため
avcC が空（8 バイトのヘッダのみ）になり、再生できない。2 段目に TS を渡して
SPS/PPS を解析させると、正しい avcC を持つ init セグメントができる。
中間を MPEG-TS にしたのは、FIFO を 2 本使うと ffmpeg 同士が出力のオープンで
待ち合ってデッドロックするため。1 本のパイプで済ませられる。

**起動時に取りこぼさない工夫。** 下流の ffmpeg が入力の probe に数秒かかる
あいだ、`siano-ts` の TS キュー（既定 256 スロット ≒ 2 秒）があふれて先頭を
落とし、MPEG-2 デコーダが固まることがあった。対策として次の 2 つを入れた。

- `TS_QUEUE_SLOTS` を 1024（約 8 秒）へ拡張
- パイプラインの先頭で 4 秒待ってから選局を始める（`PIX_START_DELAY`）

**`--fail-on-drop` は常用しない。** 起動直後の 1 回で `siano-ts` が
`No buffer space available` を出して終了する。詰まりの診断には有効。

### 注意点

- `siano-ts` のデバイス指定は `bus:address` 形式。再起動でアドレスが変わるので `--list` で確認する
- `torne-b25` の出力は正常（映像PES 450/450 が正しい開始コード）。以前「6.7%破損」と記録したが、検証スクリプトのオフセット計算（`4` と `5+afl` の取り違え）による誤りだった
- `ffmpeg` の `Invalid frame dimensions 0x0` は、PMT にある未対応ストリーム（データ放送など）に対する警告で、映像変換には影響しない

## USBホストが動作しない件（解決済み・記録）

PX-S1UD とカードリーダーが USB ポートで認識されない。キーボード・マウスでも同じなので、デバイス種別の問題ではなく USB ホスト自体が機能していない。Android（vendor カーネル 4.9）では動いていたため、mainline 6.18 と DTS の組み合わせに原因がある可能性が高い。

調査の経緯、実測したレジスタ値、試して駄目だったこと、次に疑うべき点は [USBホスト調査引き継ぎ](usb-host-investigation.md) にまとめた。要点だけ書くと、xhci のレジスタは設定済み（`USBCMD=0x5`、`CONFIG=0x40`）なのに割り込みが 3 回で止まっており、ポートレジスタへの書込みも反映されない。dwc2 は GHWCFG2 が `0x8`（デバイス専用）でホストになれない。

`siano-ts`（aarch64）とファームウェア `isdbt_rio.inp` は配備済みなので、USB さえ通れば受信できる状態にはなっている。

## NAS の録画管理への登録（mDNS と番組境界）

NAS の録画管理（`http://192.168.99.80:40776/`）に STB を登録し、番組として
録画・CM カットまで通すための実装。dtv_android と同じプロトコルに合わせている。

### mDNS

`c_src/mdns_announce.c` をそのまま Linux 側へ移し、`stb_streamer` から起動する。
`_pixstb._tcp.local` を広告し、TXT に `name` `ch` `ip` `ver` を載せる。
NAS の `pix_stream_manager` はこれを受けて `/api/discovered` に出す。

- インスタンス名は Android と同じ `pixstb-<IP の4オクテット>`。この個体は `pixstb-c0a8636d`
- ネットワークが上がる前に init から起動されることがあるので、IPv4 が取れるまで 2 秒間隔で最大 2 分待つ
- 広告が出れば `/api/nodes` への POST で登録できる。登録後は管理画面の一覧に載り、`state=recording` になる

### 番組境界（pixb）

NAS のレコーダーは `pixb` ボックスを見て番組を区切る。これが無いと
`max_segment_sec=0` のため区切りが生まれず、ファイルが作られない。
Android は EIT から番組情報を作っているので、同じことを Linux でも行う。

- `eit_watch` を `torne-b25` と `ffmpeg` の間に挟む。TS をそのまま流しながら
  EIT（PID 0x12、table_id 0x4E）の present/following を読み、service_id /
  event_id / 開始時刻 / 長さを `/dev/shm/pix/program.txt` に書く
- `stb_streamer` は `moof` の直前でそのファイルを見て、番組が変わっていれば
  44 バイトの `pixb` ボックスを差し込む。レイアウトは `fmp4_sink.c` の
  `emit_boundary_box` と同じ
- NAS は `pixb` を受けて区切り、アーカイブ EPG から番組名を引いて保存する

### 実装中に踏んだ点

- EIT のイベントはセクションヘッダ 14 バイトの後ろから始まる。11 バイトで
  読んでいて何も取れなかった
- この端末は RTC を持たず起動直後は 1970 年を指す。EIT の開始時刻と現在時刻を
  比べて「未来なら捨てる」と、放送中の番組を全部捨ててしまう。時計が合って
  いれば放送時間に現在時刻が入るイベントを選び、合っていなければ前へ進む
  方向でいちばん早いものを選ぶようにした
- NHK の present/following は「次の番組」だけを載せることがある。その場合
  EIT からは放送中の番組を確定できないので、名前は NAS 側の時計で決まる
- `pkill` はこの busybox に無い。PID を拾って kill する

`bcasd` は `cards=2`、`clients_per_card`、`max_clients` で同時接続を決める。
カードは 2 枚（SCM Microsystems SCR 3310 が 2 台）で、1 枚あたり 4 台、
合計 8 台まで受けるようにした。

```
# /etc/bcas/bcasd.conf
cards=2
max_clients=8
clients_per_card=4
allow=192.168.99.0/24
```

変更前に `/etc/bcas/bcasd.conf.bak-<日時>` へ控えを取っている。反映は
`sudo systemctl restart bcasd`。**`SIGHUP` ではトークン一覧しか読み直さない**ので、
接続数の変更には再起動が要る。`bcasd` の実装上の上限は `MAX_CLIENTS = 8`。

### 確認結果

| 同時接続 | 結果 |
| --- | --- |
| 1〜8 本目 | `ok`（8 本まで成立） |
| 9 本目 | `status=-2`（満杯） |

再起動後のログは `bcasd listening on 192.168.99.10:40790 cards=2 max_clients=8`。
登録済みクライアントは `stb1`〜`stb5` の 5 台で、X96Max_P は `stb5`。
接続すると `client stb5 from 192.168.99.109 -> card0` と割り当てが記録される。

### 負荷の見積り

ECM は最短 1 秒間隔で更新され、1 回の処理は実測 41〜56 ms である。1 枚 4 台なら
ρ ≈ 4 × 1 × 0.05 = 0.2 で、まだ余裕がある。同じ番組を複数で見る場合は ECM の
応答が 5 秒キャッシュされるため更に軽い。ただし特許文献には 1 ECM の最大処理
時間を 800 ms とする想定もあり、その条件下では 4 台で ρ ≈ 3.2 になって破綻する。
**8 本に増やした後は、実際に 8 番組を同時に復号させて遅延とドロップを測る必要がある。**

### 8 本同時の負荷試験（2026-11-11）

実際の放送から取った ECM を 8 本同時に流して測った。手順は次のとおり。

1. `siano-ts` で 60 秒の生 TS を取り（`/tmp/raw.ts`、129 MB、tmpfs）
2. `ecm_dump --pid 2305 --pid 2306` で ECM セクションだけ抜く（6.8 KB、62 件）
3. `tools/bcas-load-test.py` で 8 本から同時に `90 34` を送る

ECM の APDU は `90 34 00 00 <len> <section[8:]> 00`。セクション先頭 8 バイトは
付けず、CRC は付ける。先頭 8 バイトを残すと `0xa102`、CRC を削ると `0xa106` が
返り、どちらも購入済みにならない。実際に試して `section[8:]` が `0x0800`
（購入済み）になることを確かめた。

| 条件 | 結果 |
| --- | --- |
| 単発 | p50 53 ms |
| 8 本・実レート（合計 4.2 req/s） | p50 86 ms、p95 90 ms、最大 122 ms、失敗 0 |
| 8 本・飽和（合計 38 req/s） | p50 18 ms（ECM キャッシュ）、p95 213 ms（カードへ）、失敗 0 |

8 本を同時に開始すると全員が同じ瞬間に送って待ち行列ができ、p50 が 182 ms に
なった。実際の受信機は ECM のタイミングがばらばらなので、開始を 1.9/8 秒ずつ
ずらして測り直した値が上の 86 ms である。

**8 本は十分に収まる。** 必要量は合計 4.2 ECM/秒で、1 回 50 ms とすると 2 枚
合計で 21% の使用率になる。飽和試験でも 38 req/s まで失敗が出なかった。

`192.168.99.10` の `bcasd` は同時接続を受け付けるが、**1 台の STB から同時に
2 本以上を復号することは、いまの `cardrelay` ではできない**（後述）。

### 注意点

- 1 台の STB から同時に 2 本以上を復号することは、いまの `cardrelay` ではできない。
  接続を受けて `serve_one()` を最後まで処理してから次の `accept()` に戻る逐次実装
  のため、2 本目は待たされる。複数本を 1 台で使うなら、クライアントごとに
  スレッドを立てる改造が要る。
- 現状は 1 台 1 本（チューナー 1 本）なので支障はない。
- カード 1 枚に集約した時点で単一障害点になる。.10 が落ちると全録画が止まる。

## macOS側の再開・更新

`scripts/build-linux.sh` は停止中の専用Colimaを起動し、明示したDocker contextを使う。ビルドツリーはLinuxの名前付きvolume `x96max-build` にある。毎回 `x96max_defconfig` を適用するので、設定は `configs/x96max_defconfig` とkernel fragmentなどの管理ファイルへ反映する。

kernel設定変更時は必要に応じて次を順番に実行する。対象付き実行だけでは `output/` へ成果物をコピーしないため、最後の通常ビルドまで行う。

```sh
./scripts/build-linux.sh linux-reconfigure > work/build/kernel-reconfigure-next.log 2>&1
./scripts/build-linux.sh > work/build/build-next.log 2>&1
```

Buildrootはすべての設定変更を自動で完全再ビルドするわけではない。特にtoolchainやlibcを変更する場合は、この増分手順をそのまま使わず、影響を確認する。今回は採用版を維持して最小変更で進める。

SDは現在X96Maxの稼働rootfsである。更新のため取り外すときは、UARTから正常終了させて電源状態を確認してからmacOSへ移す。作成時の `/dev/disk8` を固定値として再利用せず、接続後の媒体・容量・内容を確認する。許可された元の媒体とは違う媒体を消去する場合は確認が必要である。ホストのrawディスク操作とTerminal自動操作は前回制限されたため、必要ならユーザーのTerminalで具体的なコマンドを実行してもらう。権限拒否を同じ経路で繰り返さない。

カーネルだけを差し替える場合は、SD全体を書き直さずFAT区画の `Image` を置き換えられる。FATラベルは `X96BOOT`、128 MiB、先頭1 MiBのオフセットである（`board/x96max/genimage.cfg`）。macOSが自動マウントしたら次を実行し、書き込み後のSHA-256が `output/SHA256SUMS` と一致することを確認してから取り出す。`--erase` を伴う `write-sd.py` は使わない。

```sh
shasum -a 256 output/Image
cp output/Image /Volumes/X96BOOT/Image
shasum -a 256 /Volumes/X96BOOT/Image
diskutil eject /Volumes/X96BOOT
```

rootfsは#1のままで動くが、`/lib/modules/6.18.62` に不要な `pwm-meson.ko` が残る。再起動後は `lsmod`、`ls /sys/class/pwm`、`cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_available_frequencies`、`for r in /sys/class/regulator/regulator.*; do cat $r/name; done` を読み、モジュール読込みなしに `pwmchip0/1` と `cpufreq-dt` が存在することを確認する。
