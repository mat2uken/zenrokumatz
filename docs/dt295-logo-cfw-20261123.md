# CFW 経路での局ロゴ取得の試行（2026-11-23）

[dt295-station-logos](dt295-station-logos.md) の続き。装置のロゴ置き場が空になり、
週次取得も `dt295-cfw` では「BS-15 を選局できない」として失敗していたため、
CFW 経路で取得できるかを試した記録。

装置のロゴ置き場が空になり（再書き込みで消えた）、週次取得も `dt295-cfw` では
「BS-15 を選局できない」として失敗していたため、CFW 経路で取得できるか試した。

## 実装したこと

`pix-logo-fetch` に `dt295-cfw` の分岐を足した。純正経路はそのまま。

| チューナー | 取得コマンド |
| --- | --- |
| dt295（純正） | `pix-ts-legacy --model dt295 ... -t N` |
| dt295-cfw | `pix-cfw-grab` で選局してから取得 |

装置の `/usr/bin` に `pix-cfw-grab` と `pix-dt295-logo` があることは確認済み。
ドライランで組み立てたコマンドも確認した。CFW 側の取得部はこれである。

```sh
( pix-cfw-grab tune BS15/0x40f1 && pix-cfw-grab save - --seconds N )
  | pix-dt295-logo --out /var/lib/pix/logos --wait N
```

## 結果

| 項目 | 結果 |
| --- | --- |
| BS15 への選局 | 成功（3 MB/s で 1200 秒、3.5 GB を受信） |
| ロゴの検出 | **失敗**。パーサの記録は `waiting for service 929 (PAT 0)` |
| パイプライン | 取得後に復帰（`recording`、`totalPushed` 前進） |

`PAT 0` は、パーサが PAT セクションを 1 つも見ていないことを意味する。
その後の切り分けで、原因は 2 つに分かれた。

### 原因 1: tune の標準出力がパイプを汚していた

`pix-cfw-grab tune` は選局結果を標準出力に書く。`( tune && save ) | parser` の形では
その数行が TS の前に混ざり、188 バイトの同期がずれたまま戻らない。パーサは再同期を
しないので、以降すべてのパケットが捨てられる。

`tune >/dev/null` に変えたところ、パーサは PAT と PMT を読めるようになった。

### 原因 2: カルーセルは告知されるが、モジュールが流れない

修正後は `logo modules 0/0 in 2 carousel(s)` を記録した。PAT・PMT は読めており、
カルーセルも 2 件告知されている。しかしロゴのモジュールが 1 つも送出されていない。
1200 秒の取得を 2 回行い、どちらも同じ結果だった。

選局先は正しい。取得した TS の PAT は `101, 102, 700, 701, 707, 929` である。
929 は確かに含まれる。ログにも IF 1318000 kHz、TSID 0x40f1 へのロックが残っている。
したがって、**929 のカルーセルがロゴを送出していない**か、11 月の衛星再編で
カルーセルの構造が変わり、11-18 に作ったパーサがモジュールを数えられなくなっている。

## 次に必要な診断

1. BS-15 取得時に `pix-cfw-grab` 自身の診断（PAT 数・ロック状態）を残すこと。
   現在はパーサのログしか残らず、選局先が BS-15 だったかを確認できない
2. BS-15 がスクランブルされている場合は、`torne-b25` を挟んでから解析する
3. 装置に Python が無いので、PAT の検査は NAS 側か C の小道具で行う

## 純正ファームで取る案（未実施）

再起動するとチューナーの RAM から CFW が消え、純正ローダーに戻る。その状態なら
`pix-ts-legacy` で BS-15 を取れる。ただし純正経路を一度動かすと CFW のフックが
戻るため、CFW に戻すには USB の電源切り直しが要る。**一時的な切替ではなく
ファーム構成の変更**であり、録画方式そのものに影響する。今回は実施していない。

## カルーセルの中身を読んだ結果（2026-11-23 20:40）

取得済みの TS（40 秒）を NAS 側で解析し、929 の PMT とカルーセルの実体を調べた。

| 項目 | 値 |
| --- | --- |
| 929 の PMT PID | 1793 |
| 宣言されているストリーム | 10 本、すべて stream_type 0x0D（カルーセル） |
| カルーセルの PID | 1905〜1914 |
| うち descriptor 0x79（BS）付き | 1913 |
| 40 秒間のその PID のパケット数 | **すべて 0** |

つまり 929 はカルーセルの器だけを宣言し、中身を送っていない。パーサが
`modules 0/0` と記録したのは、この状態を正しく反映したものだった。

### まだ分からないこと

- 送信は「20 分おきに 1 分弱」とされ、まったく送らない時期もある。40 秒と 20 分 × 2 の
  窓が、たまたま送信の合間だった可能性は残る
- 取得した TS の速度は約 3 MB/s で、BS のトランスポンダ全体（6 MB/s 前後）より低い。
  半分しか運べていない場合、カルーセルがその欠けた側にある可能性がある
  （ただし取得側の診断は「0 drop, 0 resync」）

### 次の判断材料

1. 10 分程度のサンプルで、カルーセル PID にパケットの現れる時間帯を探す
2. 純正ファームで取った 11-18 の TS を残していれば、同じ PID のデータと比べる
3. 週次取得は CFW 経路で動くようになったので、04:00 の窓で再試行させる

## 多重化の完全性と、毎晩の自動再試行（2026-11-23 21:10）

「取得が多重化の一部しか運べていないのでは」という疑いを、取得済み TS で検証した。

| 項目 | 値 |
| --- | --- |
| PID 数 | 30 |
| ヌルパケット（PID 8191） | 104,408（16%） |
| 連続性カウンタの跳び | 2 PID のみ（ヌルと 1 本） |
| TS レート | 23.9 Mbps |

ヌルパケットが入り、連続性も保たれているので、取得は多重化全体を運んでいる。
**カルーセル PID にパケットが無いのは、送出が無いため**である。

20 分間の取得で DII が 1 つも届かなかった（`0/0 in 2 carousel(s)` の 0/0 は
告知モジュール数）。929 はカルーセルの器だけを宣言し、中身を送っていない時間帯が
続いていると判断する。

### 毎晩の自動再試行

送信が再開する時期を待つため、NAS 側に毎日 04:10 の再試行を置いた。

| 項目 | 内容 |
| --- | --- |
| スクリプト | `/home/ku/pix-cm/logo-retry.sh` |
| タイマー | `logo-retry.timer`（毎日 04:10、`Persistent=true`） |
| 動作 | PNG が 1 枚でもあれば何もしない。無ければ `--wait 1800` で取得 |
| 上限 | 連続 14 回で停止し、人の判断を待つ |
| 初回 | 2026-11-24 04:10 |

深夜枠なので、失敗しても録画への影響は 30 分程度に収まる。
