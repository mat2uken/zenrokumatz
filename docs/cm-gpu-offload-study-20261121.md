# CMカット処理のCPU負荷削減の検討（GPU活用の可否を含む）

対象: NAS sweedmaster02（192.168.99.80）で動く `cm-scan` / `cm-overlay` / `cm-verify`
調査日: 2026-11-21
結論の要約: **GPU（Quadro K4200）を導入するより先に、CPUだけで 7〜8 割を削れる無駄がある。
GPU は最も効かない部品に効かせる投資になる。**

---

## 1. 結論

| 順位 | 施策 | 区分 | 削減量（相対） | 実装規模 |
|---:|---|---|---:|---|
| **1** | `cm-verify` をパケット照合＋出力のみデコードへ変更 | **CPUのみ** | **−56%** | 60〜100行 |
| **2** | `cm-service` の重複 `cm-scan` 実行を削除 | **CPUのみ** | **−9%** | 3〜8行 |
| **3** | マーカー測定を `cm-scan` に統合（4パス→2パス） | **CPUのみ** | **−9%** | 60〜90行 |
| 4 | NVDEC で判定フェーズのデコードを置換 | GPU前提 | −14% | 150〜250行＋ドライバ＋ffmpeg再ビルド |
| 5 | マーカーキャッシュのヒット率改善 | CPUのみ | 上限 −28% | 判定ロジック改修（品質問題） |

**1〜3 を実施すると、CMカット1本あたりのCPUは約 2/3 減る。** 4 はここまで削った後に残る
デコード分にしか効かないため、投資対効果が最も悪い。

---

## 2. 実測した現状

### 2.1 処理時間の内訳

45分番組（81,060フレーム）を実際に処理したジョブ `135199b7` のログと成果物から復元した。

| 段階 | 内容 | 時間 | 構成比 |
|---|---|---:|---:|
| `cm-scan`（1回目） | 全編デコード＋特徴量＋マーク学習 | 366 s | 15% |
| `cm-overlay`（キャッシュ版） | 全編デコード＋ROI相関 | 338 s | 14% |
| `cm-scan`（2回目・**重複**） | 1回目と同一コマンド | 224 s | 9% |
| `cm-overlay`（学習版） | 全編デコード＋ROI相関 | 220 s | 9% |
| `cm-cut` | リムックス | 10 s | 0.4% |
| **`cm-verify`** | **2ファイル全編デコード＋毎フレームMD5** | **1,527 s** | **63%** |

**動画を4回フルデコードしている。**

### 2.2 ベンチマーク（15分クリップ・1440x1080・30fps）

NAS 上で実行。CPU 時間は子プロセスの utime+stime。

| コマンド | wall | CPU秒 | CPU秒/フレーム |
|---|---:|---:|---:|
| `ffmpeg -f null -`（デコードのみ） | 33.8 s | 320 s | 2.71 ms |
| `cm-scan`（フル機能） | 98.3 s | **345 s** | 2.92 ms |
| `cm-overlay`（キャッシュROIのみ） | 85.7 s | **305 s** | 2.81 ms |
| `cm-verify`（相当のデコード2回＋MD5） | 254.9 s | **563 s** | — |
| `ffmpeg -f framemd5`（デコード＋毎フレームMD5） | 106.2 s | 404 s | — |
| `ffmpeg -c copy -f framemd5`（**デコード無し**のパケットハッシュ） | 1.7 s | 2.8 s | — |

**`cm-scan` と `cm-overlay` の CPU 時間はほぼすべてデコード。** 画素演算の寄与は
フル解像度グレー化（実測 −1.9%）、`video.csv` 出力（−0.1%）を含めても数%に満たない。

デコードはコア数にほぼ比例する（同一クリップ、ffmpeg のデコードのみ）:

| スレッド数 | wall | CPU秒 |
|---|---:|---:|
| 4 | 84.8 s | 311 s |
| 12 | 36.4 s | 314 s |
| 自動（28） | 33.1 s | 319 s |

**CPU秒は 311〜320 でほぼ一定。** つまりデコードは「1フレームあたり一定のCPU仕事」であり、
並列度を上げても総CPU仕事は減らない。**削減するには「デコード回数を減らす」しかない。**

### 2.3 負荷の実態

```
%Cpu(s): 70.6 us, 5.3 sy, 17.6 id        load average: 19.34
```

4 ワーカーが各 3.5 コア相当を消費し、常時 14 コアを占有している。28 スレッド機の
ほぼ半分がCMカットだけで埋まっている状態。

## 3. なぜGPUが効かないか（Quadro K4200 の実力）

実機の GPU は `NVIDIA GK104GL [Quadro K4200]`。現在は `nouveau` がバインドされ、
NVIDIA ドライバ・CUDA・OpenCL ICD はいずれも未導入。

### 3.1 ハードウェアとして使えるが、効く範囲が狭い

| 項目 | 実測／一次資料 |
|---|---|
| NVDEC | Kepler Gen1 が 1 基。H.264 8bit / MPEG-2 / VC-1 対応。HEVC 非対応 |
| 公称 H.264 1080p デコード | 約 161 fps（NVIDIA 2016 年公表値） |
| NVDEC セッション制限 | 無し（エンコードの 2〜3 制限とは別） |
| SSD 転送（PCIe 2.0 x16） | 実測リンク確立済み。NV12 4本でも約 300 MB/s で帯域の 5% |
| Compute Capability | **3.0 (sm_30)** |
| sm_30 をコンパイルできる最後の CUDA | **10.2**（CUDA 11.0 で削除） |
| ドライバ 470 の CUDA | 11.4 |

**CUDA カーネルを新規に書く路線は閉じている。** sm_30 をコンパイルできるのは CUDA 10.2 までで、
Ubuntu 24.04（gcc 13）に CUDA 10.2 を入れるのは現実的でない。GPU を使うなら
OpenCL 1.2（ドライバ同梱の JIT）が唯一の現実解になる。

### 3.2 それでも効かない理由

- 現行ツールの CPU 時間の **97% 以上がデコード**。GPU に移せるのはこの部分だけ。
- しかし **そのデコードは、上の 1〜3 の施策で回数自体を減らせる。**
  1〜3 を実施した後に残るデコードは 1/3 程度になる。
- しかも `cm-scan` / `cm-overlay` / `cm-verify` は静的リンクの ffmpeg を使っており、
  実機のバイナリに NVDEC は組み込まれていない（`cuvid` シンボル 0 件、`nvdec` 0 件）。
  ドライバ導入に加えて **ffmpeg の再ビルドが必要**。しかも nv-codec-headers を
  `sdk/11.1` 以下に落とさないと 470 ドライバでは `libnvcuvid` をロードできない。

**投資（ドライバ＋再ビルド＋GPUカーネル）に対して、削減できるのは全体の 14% 程度。**

---

## 4. 推奨する対策（CPUのみ）

### 4.1 【最優先】`cm-verify` をパケット照合へ変更 — 全体の 56% を削る

**現状の無駄**: `cm-verify` は元ファイルとカット後ファイルの**両方**を全編デコードし、
**全フレームの画像プレーンを MD5** している。45分番組で 563 CPU秒、2時間番組なら
3,900 CPU秒（1時間超）。ハッシュ対象は 2時間で **364 GB** のプレーンに達する。

**代替案の根拠（実測）**: `cm-cut` はパケットを再エンコードせずコピーし、タイムスタンプだけ
シフトする。実際にカット版を作って確認した:

```
元 clip.mp4      : 6b14a88ad4e6ba22e0c2dd1118d6394c / 08d8853831b268374a65279197fe1171 ...
カット cutdemo.mp4: 6b14a88ad4e6ba22e0c2dd1118d6394c / 08d8853831b268374a65279197fe1171 ...
```

**パケットの MD5 が完全一致**（PTS のみ −39039 にシフト）。つまり
「出力パケットの MD5 が元の部分列と一致する」ことを確かめれば、**ビット同一性が直接証明**できる。
デコード後フレームの MD5 一致は、その帰結を遠回りに確かめているにすぎない。

| 検証方式 | 2時間番組の CPU | 現状比 | 保証内容 |
|---|---:|---:|---|
| 現状（2ファイル全編デコード＋フレームMD5） | 3,879 s | — | 画素一致・デコード可・PTS |
| 両方デコード＋パケットMD5 | 約 1,180 s | −70% | 同上（パケット同一性が画素一致を包含） |
| **出力のみデコード＋パケットMD5（推奨）** | **約 450 s** | **−88%** | 公開物のデコード可＋両者のビット同一 |
| パケットのみ（デコード無し） | 約 25 s | −99% | ビット同一のみ（デコード可は失う） |

**推奨は「出力のみデコード＋パケットMD5」。** 元ファイルのデコード可否は `cm-scan` が
既に全フレームをデコードして確認済みなので、`cm-verify` で二重に確かめる必要はない。
公開物（`*_CMカット.mp4`）は完全にデコード検証される。

**失われる保証と対策**:
1. 元ファイルのデコード可否を `cm-verify` としては証明しなくなる
   → 出力側フルデコードで実質代替（壊れていれば公開物のデコードで検出）
2. カット境界 GOP の参照連鎖は間接証明になる
   → 境界前後 ±N フレームの限定デコードを追加（4カットで約600フレーム＝全体の 0.3%）

**注意**: 現行の `--audio-packets-only` は名前と裏腹に**映像を常にデコードしている**
（`cm_verify.cpp:37` の条件が `packets_only` を見ていない）。このオプションは現状
CPU削減に一切寄与していない。実測でもフルデコード版と差がなかった（647 CPU秒 vs 671 CPU秒）。

### 4.2 【低リスク・即効】重複した `cm-scan` 実行を削除 — 全体の 9%

`cm_service.py` の `measure()` は、キャッシュ不一致時に
`command(scan_argv, stage / 'scan-no-cache.log')` を実行するが、これは
数行前に実行した `run_parallel` の `scan_argv` と**同一の argv・同一の出力先**である。
しかも 1 回目の `cm-scan` は既に `logo.json` と `ref-*.pgm` を書き終えている。

```python
# 現状（570行目付近）
if cached and not cache_ok:
    cached = None
    command(scan_argv, stage / 'scan-no-cache.log')   # ← 100% 純粋な重複
    learned = load(features / 'logo.json')
```

**1回目の `logo.json` をそのまま読めばよい。3〜8行の修正で 224 秒消える。**

実運用ではキャッシュがほぼ効いていない（`result.json` にキャッシュ使用の記録が 0 件、
確認できた記録はすべて `cache_unusable`）ため、**この重複は毎回発生している**。

### 4.3 マーカー測定を `cm-scan` に統合 — 全体の 9%

キャッシュされた全角マークの ROI はスキャン開始前に既知なので、
`cm-scan` のデコードループ内で ROI の加算（52×92 ≒ デコードの 0.2%）をすれば、
`cm-overlay` の実行が丸ごと不要になる。判定フェーズは 4パス → 2パスになる。

ROI 走査は学習結果に依存しないため、キャッシュヒット時も不一致時も同じ統合が効く。

### 4.4 見送ってよいもの

| 案 | 判断 |
|---|---|
| フル解像度 `sws_scale` を窓内のみに限定 | 削減は −1.9%（実測）。ただし `data[0]` 直接参照にすれば画素値は不変なので、ついでの整理としてなら可 |
| `sws` コンテキストを2本に分離 | −0.1%。コンテキスト再構築の分。3行で直るのでついでに |
| `video.csv` の行を集約 | **非推奨**。205,800 行の出力・パースは合計 0.3 秒。`gap_spans` のフレーム粒度が失われる品質リスクの方が大きい |
| `thumbs.bin` を毎回出力 | CPU はほぼ 0 だが tmpfs を 2時間で約 83 MB 消費。本番経路に読み手がいないなら条件出力に |
| Python 側の処理 | 無視できる（`measure()` 1回で約 1.1 秒） |

## 5. GPU を使うなら（将来の選択肢として）

現行ハードで GPU を使う場合の条件を整理しておく。**上記 4.1〜4.3 を実施した後の判断材料。**

### 5.1 必要な作業

1. `nvidia-headless-470` に加えて **`libnvidia-decode-470` を明示的に導入**
   （ヘッドレス metapackage は NVDEC を引かない）
2. **カーネルは 6.8 系に固定**（Ubuntu は 6.14 HWE で 470 の DKMS ビルド不可と明記）
3. 再起動して nouveau を外す（blacklist はパッケージが自動で入れる）
4. **nv-codec-headers を `sdk/11.1` 以下にして ffmpeg を再ビルド**
   （`master`(SDK 13.1) で作った ffmpeg は 470 ドライバで `libnvcuvid` をロードできない）
5. `cm-scan` / `cm-overlay` / `cm-verify` を `av_hwdevice` + `h264_cuvid` 経由に改修

### 5.2 実装上の落とし穴

- cuvid の出力は **NV12**。現行コードの `AV_PIX_FMT_GRAY8` 宣言（実体は Y プレーンコピー）は
  そのままでは通らない。`linesize` は 256 バイト境界にパディングされ（1440 → 1536）、
  coded height は 1088 で表示は 1080。**HWDEC 由来のフレームは `height` ではなく
  `linesize` と crop を意識する必要がある。**
- PAFF/インターレース素材では `deint=weave`（既定）を固定すること。それ以外だと
  フレーム数が 2 倍になり PTS も合成値になる。
- 末尾フレームが落ちる既知の不具合があり、`cm-verify` の「全編デコード」判定と衝突しうる。
  実素材でのフレーム数一致確認が必須。
- 4 ワーカー同時デコードは NVDEC 1 基を共有する。推定 200 fps に対し需要 120 fps で
  余裕はあるが、実測での確認が要る。

### 5.3 期待効果

判定フェーズのデコードを完全に GPU に移せたとして、**1〜3 実施後の全体からさらに −14%**。
ドライバ導入・ffmpeg 再ビルド・3ツール改修・品質再検証のコストに見合うかは、
1〜3 を実施して残る負荷を見てから判断するのが妥当。

## 6. 残る要因（別途の検討課題）

- **マーカーキャッシュが効いていない**。18 件のキャッシュに対し、`cache_unusable` の記録のみ。
  原因（ROI 選別の品質か、参照 PGM の不一致か）を特定できれば、判定フェーズが
  2パス → 1パスになり、さらに −9% が見込める。ただしこれは CPU 最適化ではなく
  **判定精度の問題**なので、別途の調査が必要。
- **`field_coded_unsupported` が 125 件**（全体の 5.8%）。CMカット自体を諦めている。
  パケット照合方式（4.1）にするとパケット数とフレーム数の不一致問題が消えるため、
  この制約を外せる可能性がある。要検証。
- `no_breaks`（487 件）と `too_short_to_detect`（237 件）で全体の 1/3 は判定自体が
  成立していない。無駄なデコードを避ける余地があるかは別途検討。
