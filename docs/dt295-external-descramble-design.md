# DT295 の複合をチューナー内で行わず、外で行う構成

2026-11-20。2代目（192.168.99.123、DT295・BS11）を対象に、TS をそのまま取り出して
B-CAS の複合を別段で行う構成を検討し、設計として整理する。

前提として、**`PIX_CAPTURE_SECONDS`（1800秒）ごとの意図的な切り直しを廃止すること**を
目標の1つに据える。現在これは DT295 のカード交換が止まる問題の回避策として入っている。

## 1. 検討の出発点にある誤解を先に解く

最初に出発点として想定していた「今のファームウェアは内蔵 B-CAS で複合しているから、
それをやめて外で複合する」という理解は、**ソースを全部読むと事実と違う**。ここを直さないと
設計が空回りするので最初に書く。

現在の `pix-ts-legacy`（`vendor/pix-userland`）は、**B-CAS カードに ECM を送る
APDU（`90 30` / `90 32` / `90 34`）を1行も実装していない**
（`vendor/pix-userland/src` 全体を検索して一致なし。`0x90` の一致は衛星レジスタと
DT181 側のコマンドだけ）。

実際にやっているのは次のとおり。

| 段 | 実装 | 根拠 |
|---|---|---|
| セッション認証 | DT295 内部の秘密素材との認証（`0x01010000` / `0x01020000`） | `src/dt295.c:743,762` |
| カード初期化・活性化 | **I2C 経由のファームウェアコマンド `0x0a`** | `src/dt295.c:894,915` |
| TS 鍵の取得 | `secure_command(0x07010600)` で**ファームウェアから16バイトを受け取る** | `src/dt295.c:1582` |
| 複合 | 受け取った鍵とアセット内 IV で `dt295_packet_crypto` を呼ぶ | `src/dt295.c:1885-1889` |

つまり現在の複合は **ARIB/MULTI2 の B-CAS 経路ではなく、ベンダの独自複合**である
（`dt295_crypto.c` は CBC の AES 変種。ARIB の MULTI2 ではない）。

この事実から、設計上の含意が3つ出る。

1. **「チューナー内で複合」と「外で複合」は、暗号方式そのものが違う。**
   切り替える先の `torne-b25` は ARIB MULTI2 の B-CAS 経路なので、置き換えではなく別系統への移行になる。
2. **内蔵カードスロットは、今の複合では B-CAS カードとして使われていない可能性が高い。**
   現在の経路はファームウェアから鍵をもらうので、カードに ECM を投げてはいない。
   カードは「ファームウェアが内部で使うもの」であって、ホストが PC/SC で読む対象ではない。
3. したがって**「内蔵カードリーダーをホストの PC/SC リーダーとして使う」は、
   現行の内蔵複合と競合する**。ファームウェア側は「カードの持ち主は1つ」で、
   主 FR が持っている間は ARM 経路が `FW_EBUSY`、ARM が持っている間は主 FR の
   `0x51`〜`0x57` が `FW_EBUSY` になる（`research-cfw.md` §3.6）。

### 1.1 なぜこれで「録画が止まる」のか

内蔵複合では、カード交換（I2C コマンド `0x0a`）がファームウェア状態 `0x11` を前提にする。
`kill -9` やパイプ詰まりで `0x11` から外れると、`dt295_boot` が
`firmware boot requires cold state 0 or unauthenticated state 16` で落ちる。
復帰はアイドルイメージ再ロード → ソフトリセット → USB unbind/bind の順で重く、
最後の手段は機体ごと沈黙した前科がある（`pix-stream-simple:428-439`）。

**1800 秒の切り直しは、この「状態が壊れる前に自分から止めて作り直す」ための保険**である。
根拠は `docs/recording-split-and-stb-recovery.md:36-37`（「この切り直しは DT295 の
カード交換が止まる問題を避けるための技術的措置なので、STB 側の周期は維持する」）。

## 2. 何が「カード交換が止まる」を起こしているのか

外部複合の経路（`PIX_DECRYPT=1`、`pix-stream-simple:299-339`）は既に実装されている。
そこでは `pix-ts-legacy | torne-b25 | pix-ring …` の形になる。
このとき止まる原因は、コードを読むと複数あり、**対策が別々に要る**。

| # | 止まり方 | 根拠 | 対策 |
|---|---|---|---|
| A | `pix-ts-legacy` の出力が 3 秒詰まると自分から落ちる | `main.c:88-90`（`TS output stalled for 3 seconds` → `stream_fail(8)`） | 下流に詰まらせない。TS を一時ファイル/リングに逃がす |
| B | 受信キュー 1024 スロットが満杯になると即致命 | `main.c:109-117`（`--fail-on-drop` は no-op で常に致命） | 同上 |
| C | `torne-b25` が下流の `write` で止まると、`stdin` の `read` も止まる | `torne_b25.c:16-21`（`emit` は書き切るまでループ） | 復号器の後に十分なバッファを置く |
| D | カード側の待ち（PC/SC）が 15 秒でタイムアウトする | `card_client.c:17`（`SO_RCVTIMEO` 15 秒） | カード経路の遅延を 15 秒未満に保つ |
| E | ECM（PID 289）を流さないとカードセッションが約 17 秒で切れる | `docs/second-unit-provisioning.md:243` | PID を絞るなら ECM を必ず残す（後述） |
| F | デスクランブラがカードセッションを失っても、`put` が負を返して開き直す | `torne_b25.c:59-70` | 既に対策済み（20 回まで 500ms 間隔） |

**A〜C は「下流の詰まりがカード交換まで伝わらないようにする」問題**で、
**E は「ECM を流し続ける」問題**である。両者は独立に解決できる。

## 3. 選択肢の比較

「1800 秒の切り直しをやめる」を目標に置くと、切り方は3つある。全部は排他で、
段階として積める。

### 案1: 切り直しを長くするだけで、方式は変えない（最小）

`PIX_CAPTURE_SECONDS` を 1800 → 21600（6時間）などに延ばす。
**切り直しが起きる頻度が下がるだけで、起き方（カード交換で状態が壊れうる）は変わらない。**

- 利点: 設定1行。`pix-ts-legacy` の `-t -` も使えるので、実は今日から無期限にできる
  （`main.c:402`、`-t -` は SIGTERM まで）。
- 欠点: `-t -` にすると、**状態が壊れたときに自然復帰しない**。今の復帰は「プロセスが
  1800 秒で終わる → ランチャーが作り直す」に依存している部分がある。
- 判定: **単独では採らない。** ただし案3 の土台としては必須。

### 案2: 外部複合に切り替え、現行のまま組む（既にある形）

`PIX_DECRYPT=1`。`pix-ts-legacy | torne-b25 | pix-ring | …`。

- 利点: 実装済み。BS11 で `card_commands=48 failed=0` の記録がある
  （`docs/second-unit-provisioning.md:236`）。
- 欠点:
  - `PIX_DECRYPT=1` にすると **`dt295_recover`（USB 回復）が一切走らなくなる**
    （`pix-stream-simple:497,500`）。今より復帰が弱くなる。
  - まだベンダの複合鍵をファームウェアから取っている（§1）ので、
    「外で複合する」にしても**内蔵カードへの依存は消えていない**。
  - `run_buffered` は再同期 ffmpeg を挟まない（`pix-stream-simple:299-339`）。
    レガシー経路は挟んでいる（`pix-stream-linux:256-263`）ので、不整合がある。
- 判定: **単独では採らない。**

### 案3: ファームウェアを差し替え、生 TS を常駐で出し、外で B-CAS 複合する（本命）

MB8AC031-CFW に差し替え、**TS をファームウェアから直接・連続的に取り出す**。
複合は既存の `torne-b25` に、**DT295 の内蔵カードスロットを PC/SC で見せたもの**を渡して行う。

- 利点: ファームウェア状態機械（`0x11` など）への依存がなくなる。チューナーは
  「生 TS を出す装置」になり、カードは「カードリーダー」になる。役割が分離する。
- 欠点: ファームウェアの常駐ストリームが未実装（後述）。選局もホストの仕事になる。
  カードの持ち主がファームウェアの内部複合から ARM に移るため、
  **内蔵複合は使えなくなる**（`FW_EBUSY` の関係。§1）。
- 判定: **本命。ただし段階を踏む。**

## 4. 案3 の構成

```
                    ┌──────────── MB8AC031-CFW（差し替え）────────────┐
  生 TS（非複合）    │  リング 4 MiB（0x02000000）                      │
  ◀──── bulk EP0x81 ─│  ← ホストが STREAM 枠で汲み出す                    │
                    │                                                  │
  カード APDU        │  ARM コアの svc_card（CARD_ON/PARAM/XFER）        │
  ◀──── EP0 枠 ──────│                                                  │
                    └──────────────────────────────────────────────────┘
        │                                   │
        ▼                                   ▼
  生TS（EP0x81のバルク）               PC/SC（pcscd → libifd → EP0）
        │                                   │
        ▼                                   ▼
  stb-capture（常駐・詰まらない）──┐    bcasd ── cardrelay ── /dev/shm/torne/card.sock
        │                          │                                   │
        ▼                          │                                   │
  torne-b25 ◀──────────────────────┘                                   │
        │
        ▼
  eit_watch | ffmpeg(encode) | ffmpeg(frag) | stb_streamer
```

現行との差分は「`pix-ts-legacy` が担っていた、受信・選局・複合鍵取得を分ける」ことにある。

### 4.1 常駐ストリームがない問題（最優先）

`stream.c` は明示的に「主ループが無い」と書いている（`research-cfw.md` §1.4）。

> There is no main loop here. A frame arrives, we are called, we return.
> It means "move what you can now, and tell me what you did", and the host comes back.

1 枠で最大 64 バースト = 32 KiB。UHF 3.72 MB/s を出そうとすると **毎秒約114回**の
制御転送が要る。しかも `tsout_push` は端点が空いていなければ**待たずに** `FW_EAGAIN` を返す。

**「EP0 を流し続ける」方針は、この点でそのままでは破綻する。** 録画を止めないことを
条件に置くと、ホスト側ポーリングでは次のどちらかが起きる。

- ポーリングが遅れるとリングが満ちる。selene でそれが起きると何が起きるかは
  **文書に無い（未確認）**。dione では「止まっている間の入力は失われる」と実測されている。
- ポーリングを最優先にすると、カードの枠が EP0 を待たされる。

解決の方向は3つあり、**併用する**。

#### (a) ファームウェア側に常駐の送出ループを作る【要改変】

EP0 の枠処理と別に、リング → EP 0x81 を**ファームウェア内で**回し続ける。
ホストは EP0 に来なくてよい。リングが満ちたら上書きせず待つ（dione はそうなっている）。

- 難点: 「主ループが無い」のは、FRC1 経路では常駐ローダの 1 回の制御転送の中で
  走っており、枠を返すまで他の枠を受けられないから。常駐ループを入れるには、
  **枠の処理から抜けて自前のループに戻る**設計変更が要る。
  既存の `ts_grab` はホスト側スレッドで回しているので、その知見は使える。
- 難点2: `docs/arm.md:255-257` は「EP の窓は主 FR が扱う。別のコアから書くと
  TS が欠ける（実測）」。**送出ループは主 FR 側に置く**必要がある。
- 判定: **本命だが工数が大きい。** 段階4 に置く。

#### (b) リングを大きくする【要改変・小】

リングは `0x003FFFC0`（4 MiB、21,845 記録）で固定（`tsif_selene.c`、`src/shared/regs_selene.h`）。
DT295 の `0x02000000` は先頭が `MB8AC031`、`0x02100000` から先は `0xF0F0F0F0`
（`docs/ts.md` の実測）。**4 MiB を超えて安全に使えるかは未確認**なので、
ここは実測から入る。

- 効き目: 4 MiB は UHF 3.72 MB/s で約 1.1 秒、**BS/CS では約 0.85 秒**。
  16 MiB にできれば約 4.4 秒（BS は約 3.4 秒）。ホストのポーリングの揺らぎを吸収できる幅が広がる。
- **独立した傍証**: コミュニティの `pix-dt295` も同じ 4 MiB を使い、純正ファームの 192 KiB と
  比べて「1 秒ごとに 600 ms 止める試験で、192 KiB は CC 飛び 95 件・約4割欠け、
  4 MiB は欠け無し」を実測している（`research-ecosystem.md` §355-363）。
  **リングは実際に効く。ただし 4 MiB で足りるのは「一時的な詰まり」までで、
  恒久的に汲み出しが止まる構成では足りない。**
- 判定: **(a) を作るまでの緩衝。** 単独では解にならない。

#### (c) ホスト側の汲み出しを専用スレッドにする【ホスト側のみ・必須】

`ts_grab` の `cmd_save_selene` がやっているとおり、読み出しスレッドを回して
STREAM を隙間なく積む（`research-cfw.md` §9）。これを常駐デーモンにする。

- 効き目: 制御転送の往復回数が律速になるが、1 枠 32 KiB を途切れなく送れる限り成立する。
- 判定: **(a) が入るまでの実用解。** (a) が入っても、受け取り側として必要。

**この3つを合わせた判断**: まず (c) をホスト側で作り、(b) でリングを広げ、
余力があれば (a) でファームウェア側の常駐ループを入れる。
(a) が入るまでは「EP0 を流し続ける」が前提になるので、**カードの枠が待たされる
ことを前提に設計する**（4.2）。

### 4.2 カードとの競合（EP0 を流し続ける前提で）

重要な事実が2つある。

1. **カードの処理そのものは、TS の枠が EP0 を占めている間も進む。** ただしこれは
   **ARM 経路**の話（`docs/card.md:216-218`）。待ちが ARM の中で済むため。
   `ARM_CALL` / `ARM_REAP` という枠自体は EP0 を通るので、そこは待たされる。
2. **主 FR のカード経路（`0x51`〜`0x57`）は複数枠を要する。** `card_on` だけで
   段階1/2/3 と ATR ポーリングで最低4枠（`card.c:287-318`）。
   **EP0 を流し続ける構成では、主 FR 経路は使えない。**

したがって**カードは ARM 経路（`CARD` サービスの `ON`/`PARAM`/`XFER`）一択**にする。
1 ブロックが `ARM_CALL` + `ARM_REAP` の 2 枠で完結する（`svc_card.c`）。

さらに、**カードの持ち主を ARM に固定する**。ARM が持っている間、主 FR 経路は
`CARD_STATUS` 以外すべて `FW_EBUSY`（`card.c:89-99`）。逆に主 FR が電源を入れている間は
ARM の `ON` が `FW_EBUSY`（`arm_ipc.c:64-79`）。**どちらか一方に決めないと、
両方を使うコードが混在して片方が恒久的に拒否される。**

| 決めること | 値 | 理由 |
|---|---|---|
| カードの持ち主 | ARM-E（固定） | TS と並行できる唯一の経路 |
| 主 FR 経路（`/dev/ifd` 経由の card.c） | 使わない | EP0 競合で ATR が間に合わない |
| IFD ハンドラ | `CFW_CARD_ARM=0` | 上記と一致させる |
| 極性 | 機種表の 1 | `dt295.json` の `card.polarity=1` |

**~~未解決の矛盾~~ -> 実機で解決済み（2026-11-20）**: ここに「`card.md` と
`svc_card.c` と `card_link.h` が噛み合わず、DT295 では ATR が来ない計算になる」と
書いたが、**実機で試したら逆だった**。

| ON の引数 | 実機の結果 |
|---|---|
| **0** | **ATR 取得成功**（13 バイト、`3B F0 12 00 FF 91 81 B1 7C 45 1F 03 99`） |
| 1 | E_TIMEOUT |

`card_link.h` が 0 を渡すのが正しく、文書もコードもそのままでよい。
**ここの読み違いで「段4 の関門」だと考えていたが、関門ではなかった。**
詳細は [unit2-stage4-card.md](unit2-stage4-card.md)。

そのままコードに従うと **DT295 では `pol = 0` になり、ARM 経路では ATR が来ない**。
にもかかわらず `docs/card.md:224` は「PIX-DT295 の ARM-E で動く（実測）」としている。

**採用する方針**: IFD ハンドラから `ON` に極性 **1** を渡す（`CFW_CARD_POL=1` 相当を用意する）。
主 FR に頼らず、ホストが明示する形にする。これで `pol = CARD_PIN_POL` になる。
**この 1 点を最初に実機で確かめる**（段4 の1）。ここが通らなければ段4 は止まる。


### 4.3 PC/SC の IFD ハンドラ（Linux で使うための前提）

MB8AC031-CFW の IFD ハンドラは既に Linux 向けビルドを持つ（`sample/ifd/Makefile` が
`uname -s` で分岐、`libifd_m2tv.so`）。ただし README の記載は
**「ビルドと pcscd の読み込みは実測。USB 機器を接続した Linux での動作は未確認」**。

そのため、既存の `bcasd → cardrelay` をそのまま使えるとは考えず、次の順で確かめる。

1. Linux で IFD をビルドし、pcscd がリーダーとして列挙するところまで（機器なしで可）
   - **注意**: DT295 は CCID クラス（`0x0B`）を名乗らないので、pcsc-lite は自動では
     リーダーとして拾わない。**IFD の `.so` をドライバ置き場に置き、機器をそのドライバに
     結び付ける設定が要る。** これは macOS 版の `Info.plist` の `ifdVendorID` /
     `ifdProductID` に相当する作業を Linux で行うことになる。
2. DT295 を挿して ATR が取れるか
3. APDU を1往復（`CFWAllowAPDU` に相当する許可が Linux 版に要るか確認）
4. `bcasd` が `reader.N` でこのリーダーを掴めるか（今は index 0 固定で選ぶ可能性がある）

**注意**: `bcasd` は `SCARD_SHARE_EXCLUSIVE` + T=1 で接続する（`bcasd.c:374`）。
pcsc-lite はリーダー単位で APDU を直列化するので、`card_tool` などが同時に開くと
`SCARD_E_SHARING_VIOLATION` になる。**診断用のツールを録画中に走らせない。**

### 4.4 ECM を流し続けること

外部複合にすると、ECM（PID 289）を流さないとカードセッションが約 17 秒で切れる
（`docs/second-unit-provisioning.md:243` の実測）。

`PIX_PIDS` を絞る方針は維持しない。その判断の裏づけは次のとおり。
ARIB のスクランブル鍵は**ECM 単位**で、その ECM に結び付いた ES だけが
復号される（`research-ecosystem.md` §1）。したがって:

- **絞るなら「使う ECM 1本 + それに結び付く ES + PAT/PMT/CAT」**を残す。ECM を落とすと復号できない。
  つまり**絞ると事故の余地が増えるだけで、得るものが小さい。**
- 地上波と BS は TS 内の ECM が1本で足りた実測がある（`smpn2/pix-dt295 docs/device.md`）。
  **CS110 はプログラムごとに ECM が別**（同資料）。2代目は BS11 なので今は1本で足りるが、
  CS に広げるなら ECM を複数残す必要がある。
- **2代目（BS11）の答え: 絞らない。** 生 TS をそのまま渡す。
  今の `PIX_PIDS="0 17 18 257 273 289 320 321"` は外す。
  帯域が問題になったときの最適化として後回しにする。

> 補足: 現行の内蔵複合では `PIX_PIDS` を絞っていても問題なかった。これは
> **ベンダ独自の複合が PID に関係なく TS 全体に効いている**ためと考えられ、
> 外部 B-CAS 複合に移すと前提が変わる。ここは移行時に必ず見直す点。

## 5. 段階

各段は独立して戻せる。段を飛ばさない。

**2026-11-20 に順序を組み替えた。** 当初は 2 → 3 → 4 だったが、段2（外部複合）が
純正ファームでは原理的に成立しないことが分かったため、3 → 4 → 2 に変えた。
根拠は [dt295-internal-card-feasibility.md](dt295-internal-card-feasibility.md)。

| 段 | 内容 | ファーム改変 | 期待される効果 | 戻し方 |
|---|---|---|---|---|
| 0 | 事実確認（無改変） | 不要 | 現行経路で生 TS が出せるか、内蔵カードが APDU に答えないことの確認 | — |
| 1 | `-t -` で 1800 秒切りをやめる | 不要 | **切り直しが消える。分割の原因が1つ減る**（実施済み） | `PIX_CAPTURE_SECONDS=1800` に戻す |
| **3** | **MB8AC031-CFW 導入、生 TS を常駐で取り出す** | **要** | **複合前の生 TS が出せる。状態機械依存が消える** | FRC1 を外す（抜き差しで RAM に戻る） |
| **4** | **内蔵カードを PC/SC 化し `bcasd` に繋ぐ** | **要** | **内蔵カードがホストから見える** | IFD を止める |
| **2** | **`torne-b25` を挟んで外部複合** | 不要 | 複合の方式が段3・4の上で変わる | `PIX_DECRYPT=0` に戻す |
| 5 | ファーム側の常駐送出ループ（EP0 を回さない） | 要（大） | EP0 競合の解消。カード遅延が安定する | 段3 のポーリング版へ戻す |

### 段1 の詳細（最初にやる、無改変）

**これを先にやる理由**: ファームウェアに手を入れる前に、「切り直しをやめても録画が
保つか」を確かめられる。ここで駄目なら、段3以降の前提が崩れる。

1. `pix-ts-legacy` の `-t -`（無期限）を使う。全ランチャーが常に有限の `-t` を
   渡しているので（`pix-stream-simple:290,305` ほか）、`PIX_CAPTURE_SECONDS` を
   `-` にしたときの扱いを定義する。

   引数解析の実装は `main.c:402-406` で、`-` だけが無期限になる。数値は
   `number()`（`main.c:168-178`）が受けるので次の制約がある。

   | 書き方 | 結果 |
   |---|---|
   | `-t -` | 無期限（SIGTERM まで）。`seconds=0` |
   | `-t 0` | 不正終了（`!v` で弾く） |
   | `-t 99999999999` | 不正終了（上限 `86400*365` 秒 = 365日） |
   | 空文字 `-t ""` | 不正終了（`!*p` で弾く） |

   **`PIX_CAPTURE_SECONDS` を空にすると `-t ""` になって即 usage 終了する**ので、
   無期限は必ず `-` を明示する。また `strtoul(...,0)` の基数0解析なので
   `01200` は 8 進（=640 秒）になる。**先頭 `0` の値を書かない。**
2. 下流の詰まり対策が要る。`pix-ts-legacy` は 3 秒で落ちる（`main.c:88-90`）ので、
   `eit_watch | ffmpeg` の詰まりが直結しないよう、**TS をリングに逃がす**
   （`pix-ring` は既にある。`run_buffered` が使っている `PIX_RING_MB=32`）。
3. 状態が壊れたときに自然復帰しないので、**`dt295_recover` を維持したまま**、
   監視で「TS が来ない」を検出したら作り直す経路を残す。
   `PIX_DECRYPT=1` のとき `dt295_recover` が無効になる穴
   （`pix-stream-simple:497,500`）はここで塞ぐ。

**合格条件**: 6時間以上、`/v1/status` の `totalPushed` が単調増加し、
NAS 側の録画が 1 ファイルで継続し、`simple: pipeline stopped after` が出ない。

### 段3 の詳細

- `ts_grab` のポーリング部を常駐デーモン化する（`research-cfw.md` §9、`cmd_save_selene`）。
- 選局はホストが `I2CXFER` で行う（`fe_dt295.h` の列を移植）。
  **現在の `pix-userland` の選局 I2C 列は使えない**（ファームウェア前提が違う）。
- 状態機械（`0x00/0x10/0x11`）への依存が消えるので、`dt295_recover` 系の
  重い復帰は不要になる見込み。ただし `CARD_ON` 直後が答えないことがある既知の問題
  （`docs/card.md` の「分かっていないこと」）は ARM 経路でも起きうる。

## 5.1 各段の合格条件

前の段の合格条件を満たすまで次に進まない。数値は「失敗を合格と読み違えない」ための最低線。

### 段0（事実確認、無改変）

| 確かめること | 方法 | 期待 |
|---|---|---|
| 現行の `PIX_PIDS` 構成で、ECM が実際に乗っているか | 短時間キャプチャを保存し PID を数える | 289 が存在する |
| 現行の複合が APDU でないこと | `pix-ts-legacy` 実行中に `bcasd` のログが動かないこと | カード要求が出ない |
| 内蔵カードが外部から見えないこと | `pcscd` 起動時にリーダーが列挙されないこと | 列挙 0 件 |

**これはファームウェアを差し替える前の記録**なので、必ず残す。ここが無いと、
後で「昔はどうだったか」を言えない。

### 段1（`-t -` 化）

| 項目 | 合格 |

### 段3（CFW 導入・常駐キャプチャ）

| 項目 | 合格 |
|---|---|

## 6. リスクと、それに効く受け入れ条件

| リスク | 影響 | 確認方法 |
|---|---|---|
| ファームの常駐ストリームが作れない | 段3 が止まる | 段1〜2 で運用は続く |
| ARM 経路で極性が合わず ATR が来ない | カードが使えない | 段4 の最初に ATR 確認 |
| Linux 版 IFD が USB 機器で未検証 | 段4 が止まる | 段4 の1で ATR |
| ring-full の挙動が DT295 で未確認 | TS 欠け | 段3 で長時間試験＋CC エラー計測 |
| カード待ちが 15 秒を超える | セッション断 | `B25_STATS failed=` と `B25_WAIT` を監視 |
| 内蔵複合に戻れなくなる | 復旧路の喪失 | FRC1 は RAM 常駐なので抜き差しで戻ることを事前確認 |

## 7. 未確定・要実測

設計上、決め打ちにできない点を明示する。

1. **DT295 でリングが満ちたときに失われるか。** 文書に無い（dione のみ実測）。
2. **DT295 で TS とカードを同時に使ったときの遅延。** 実測は GV-M2TV のみ。
3. **`--trace` が復号成否を変えるという既存の主張は、コードから説明できない**
   （`torne_b25.c:43` の O_EXCL と `ts_stats.c:24` の PES 出力だけ）。この挙動に
   依存した設計はしない。段2 で再確認する。
4. **ARM `ON` の極性**（4.2 の矛盾）。
5. **`0x02000000` 以降に 4 MiB を超えてリングを置けるか。**
6. **常駐送出ループを主 FR に置いたとき、`0x0190xxxx` の取り込みが追従するか。**

## 8. この設計でやらないこと

- **チューナー内で複合をやめた上で、内蔵カードを「録画と同時に」B-CAS として使う案は採らない。**
  カードの持ち主が排他なので、片方を選ばないと必ず `FW_EBUSY` で詰まる。
- **`PIX_PIDS` を絞る前提は捨てる。** 外部複合では ECM が要る（4.4）。
- **既存の `pix-stream-linux`（レガシー）に DT295 の分岐を足さない。**
  2代目の実稼働は `pix-stream-simple` で、`pix-stream-linux` は
  `PIX_TUNER != dt295` のときだけ選ばれる（`S97pix-stream:46`）。
  `PIX_DECRYPT` と `PIX_DT295_DESCRAMBLED` の二重定義は、レガシー整理の別課題とする。

## 10. 実装の記録

### 段1（2026-11-20 実装済み、ファームウェア無改変）

| 計画の項目 | 実装 | 変更したファイル |
|---|---|---|
| `-t -` を到達可能にする | `capture_seconds()` を追加し、`-` はそのまま、空・未設定・`0` は `-` に正規化する。`run_direct` と `run_buffered` の両方がこれを使う | `board/x96max/overlay/usr/bin/pix-stream-simple` |
| 2代目の既定 | `PIX_CAPTURE_SECONDS=-`。`PIX_PIDS` を削除 | `board/x96max/ramboot-overlay/etc/default/pix-stream-linux` |
| `PIX_DECRYPT=1` で復帰が止まる穴 | 高速失敗の判定と `dt295_recover` の門を `PIX_DECRYPT` から `PIX_TUNER=dt295` に変えた。外部複合にしても USB 復帰が残る | 同上（ランチャー） |

**計画から変えた点が1つある。** 当初は「TS を `pix-ring` に逃がす」と書いたが、
実装しなかった。理由は次のとおり。

- `pix-ring --produce` はリングが満杯になると**書き手側で待つ**（`pix_ring.c` の
  「読み手が追いつくまで待つ」）。キャプチャを `|` で直接つなぐと、
  待つのは `pix-ring` ではなく**直前の `pix-ts-legacy`** になり、
  3秒で `stream_fail(8)` する性質は変わらない。
- 逃がすには書き手を独立プロセスにする必要があり、その構成は
  `run_buffered` が既に持っている（`PIX_DECRYPT=1` の経路）。直結経路に
  二重のリングを足すと、プロセスが2つ増えて監視点が増えるだけになる。

したがって段1 では**リングを挟まず、`-t` の正規化だけを行った**。
`pix-ts-legacy` の3秒ガードは残っているので、下流が恒久的に詰まる状況では
従来どおり落ちて再試行する。詰まりを本当に吸収する必要が出たら、
段2（`run_buffered` 経路）に寄せる形で入れる。

**追加したテスト**: `tests/test_capture_continuity.py`（16件）。

| 見ているもの |
|---|
| `capture_seconds` の正規化（`-`/数値/空/`0`/未設定/先頭0） |
| どちらのキャプチャ経路も生の `PIX_CAPTURE_SECONDS` を渡さないこと |
| 直結経路の後段（eit_watch → encode → fragment → streamer）が従来と同一であること |
| `dt295_recover` が `PIX_DECRYPT` に依存しないこと、`PIX_TUNER=dt295` で門番されていること |
| ループを実際に `PIX_DECRYPT=1` で走らせて復帰に到達すること |
| 2代目の既定（無期限・`PIX_PIDS` なし・`PIX_SAT_SLOT=0` 維持） |

この16件は、変更前のファイルに対しては 6 failures / 7 errors で落ちることを
確認済み（テストが本当に旧挙動を検出する）。

**実機で確かめた**（2026-11-20、2代目）: 1800秒を越えて uptime 3375 秒で
切り直し 0 回、`totalPushed` は 10 → 1664 と単調増加、番組境界
（event 36739 → 36741）を1本のストリームで越えた。詳細と手順・戻し方は
[unit2-stage1-deployment.md](unit2-stage1-deployment.md)。
NAS 側で録画が1ファイルのままかは未確認（NAS にログインできないため）。
